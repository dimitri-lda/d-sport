# Smoke и будущие нагрузочные проверки

`health-smoke.js` проверяет HTTP-контракт `/api/health/live`: HTTP 200 и JSON `status: ok`. По умолчанию он делает всего три запроса одним virtual user, ограничивает время запроса тремя секундами и завершает сценарий за 15 секунд. Redirect отключён, чтобы случайно не проверять другой адрес. Неуспешный HTTP-ответ или нарушенный контракт приводит к ненулевому exit code k6.

Запуск с установленным [k6](https://grafana.com/docs/k6/latest/set-up/install-k6/) из корня репозитория, после запуска локального окружения:

```sh
k6 run tests/performance/health-smoke.js
```

Если локальный HTTP-порт изменён:

```sh
k6 run -e BASE_URL=http://localhost:8081 tests/performance/health-smoke.js
```

`BASE_URL` — origin backend без суффикса `/api`. Сценарий использует HTTP localhost, поэтому ему не нужно отключать проверку TLS-сертификатов. При проверке HTTPS используйте сертификат с доверенной цепочкой. Не добавляйте реальный токен или пароль в URL/команду.

Smoke не обращается к PostgreSQL и Redis: это свойство проверяемого liveness endpoint. Readiness и отказ зависимостей проверяются backend-тестами и отдельной проверкой работающего окружения.

Это проверка запуска, а не доказательство производительности. В ней нет проверки 1000 RPS, latency SLO, каталога или поведения CDN. Порогов p95/p99 здесь нет, поскольку три запроса не дают полезной статистики задержек. Конфигурация небольшого фиксированного сценария соответствует [shared-iterations executor k6](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/shared-iterations/).

## Следующие сценарии

Полноценные нагрузочные сценарии добавляются отдельно после появления настоящих API и анализа `legacy`. Их запускают только на собственном или явно разрешённом target, согласовав окно, бюджет нагрузки и условия остановки. Smoke не следует превращать в нагрузочный тест увеличением VU/iterations через CLI.

Для каждого будущего запуска фиксируют версию сборки, среду/оборудование, dataset, распределение запросов, CDN hit/miss, состояние кэша, concurrency или arrival rate, p50/p95/p99 и ошибки. Вместе с клиентскими результатами собирают CPU/RAM, PostgreSQL connections/queries, Redis eviction/hit ratio, длину очереди и задержку обработки Messenger. Начинают с малой нагрузки, повышают её постепенно и прекращают при согласованных признаках насыщения.

Большой каталог и внешние интеграции не устанавливаются и не имитируются в текущем этапе.
