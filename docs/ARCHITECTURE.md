# Архитектура первого этапа

Этот репозиторий содержит технический каркас: Symfony 8.1 API, React SPA и локальное окружение Docker Compose. Бизнес-модели, предметные таблицы, каталог, корзина, заказы, авторизация и интеграции появятся только после анализа исходников в `legacy`. Ни один текущий endpoint не моделирует поведение магазина.

## Состав и границы

| Компонент | Ответственность |
| --- | --- |
| Symfony в корне: `src/`, `config/`, `bin/`, `migrations/`, `public/`, `tests/` | HTTP API, единый JSON ошибок, health checks, Doctrine, Messenger, прикладной кэш |
| `frontend/` | Технический shell SPA, маршруты интерфейса, относительный API client, состояние запросов |
| FrankenPHP + Caddy | PHP runtime, HTTPS, маршрутизация API, production-статика и SPA fallback |
| PostgreSQL | Единственная основная реляционная база; служебная таблица Messenger |
| Redis | Восстанавливаемый `cache.app` и проверка доступности |
| Messenger worker | Выполнение сообщений из отдельного async transport |
| `tests/performance/` | Минимальная HTTP smoke-проверка и место для будущих измерений |

Symfony находится непосредственно в корне репозитория; отдельная папка `frontend/` хранит SPA и её toolchain. Это сохраняет привычные команды Symfony и чёткую границу интерфейса. В контейнере корень Symfony расположен в `/app`, а production-статика SPA — в `/app/frontend-dist`, отдельно от PHP entrypoint `/app/public/index.php`.

Symfony обслуживает `/api` и `/api/*`. React Router обслуживает остальные frontend-маршруты. Неизвестный API-маршрут должен вернуть JSON с HTTP 404; его нельзя подменять `index.html`. SPA fallback применяется только к frontend-маршрутам.

Контроллеры переводят результат технических сервисов в HTTP-ответ. PostgreSQL и Redis проверяются сервисом readiness; liveness не обращается к зависимостям. У клиента есть три технических endpoint:

- `GET /api/health/live`: процесс приложения обслуживает запрос, успешный ответ `{"status":"ok"}`;
- `GET /api/health/ready`: PostgreSQL и Redis доступны, иначе HTTP 503 и безопасное состояние проверок;
- `GET /api/version`: имя приложения, окружение и версия сборки из окружения.

Liveness подходит для проверки живого процесса. Readiness показывает возможность использовать обязательные зависимости. Отключение PostgreSQL или Redis не должно превращать liveness в проверку этих сервисов. Health-ответы и API-ошибки не раскрывают DSN, пароли и stack traces.

## PostgreSQL и надёжная очередь

PostgreSQL выбран как единая реляционная база с транзакциями, ограничениями целостности и зрелыми средствами диагностики запросов. Он не определяет будущую схему магазина: на этом этапе создаётся только версионированная инфраструктурная migration для Messenger. Отдельная тестовая база отделяет тесты от данных разработчика. В production схема меняется migrations; автоматическое исправление схемы ORM не является механизмом деплоя.

Messenger использует Doctrine transport: основная async queue и failure queue хранятся в PostgreSQL. Их инфраструктура отделена от Redis cache. Успешный commit отправки сообщения обеспечивает его сохранение в базе; сохранность при аварии хоста также зависит от PostgreSQL, постоянного volume, резервного копирования и проверяемого восстановления. Doctrine transport обеспечивает доставку с возможными повторами, поэтому будущие обработчики должны быть идемпотентными. Механизм exactly-once здесь не заявляется.

Failure queue хранит сообщения после исчерпания настроенных повторов. Оператор просматривает их, устраняет причину и явно повторно отправляет сообщения. Worker запускается отдельным Compose-сервисом, ограничен временем и памятью, получает сигнал завершения и перезапускается под управлением контейнерного runtime. Новые бизнес-сообщения и обработчики сейчас не создаются.

Doctrine transport позволяет начать без дополнительного брокера. При росте очереди нужно измерять задержку обработки, число повторов, глубину queue и влияние опроса на PostgreSQL. Transport можно заменить выделенным Redis/Valkey с политикой сохранности либо брокером после определения требований доставки и измерений; такая замена не входит в этот этап.

## Redis и кэш

`cache.app` использует Redis. Это только кэш, содержимое которого приложение способно восстановить. `cache.system` сохраняет стандартный адаптер Symfony: перенос системного кэша в Redis не даёт обоснованного преимущества на этом этапе.

Локальный Redis ограничен по памяти и использует `allkeys-lru`; persistence отключена. При вытеснении ключей или перезапуске Redis теряется только восстанавливаемый кэш. Redis cache не хранит критические сообщения, долговечные данные или будущие сессии. Persistence сама по себе не исправляет риск удаления queue-ключей политикой eviction.

Соединения и readiness имеют короткие timeout. PostgreSQL и Redis не публикуют порты на хост по умолчанию. Объём Redis и стоимость cache miss выбираются по измерениям на целевой инфраструктуре. Для будущего доменного кэша отдельно потребуются правила инвалидирования, namespace/version ключей, TTL и защита от одновременного восстановления популярных ключей.

## Путь запроса

В разработке браузер открывает Vite по `http://localhost:5173`. Vite отдаёт исходники интерфейса и HMR, а `/api` проксирует во внутренний `http://backend:8080`. Прямой доступ к backend доступен по `http://localhost:8080` и `https://localhost:8443`; локальный сертификат Caddy необходимо доверить в системе, если используется HTTPS. Относительный API base URL `/api` сохраняет один origin для браузера и не требует CORS.

```text
Браузер → Vite :5173 → /api → Caddy/FrankenPHP :8080 → Symfony
                                                  ├→ PostgreSQL
                                                  └→ Redis cache
```

В production Vite собирает frontend в статические файлы. Caddy отдаёт эти файлы из `/app/frontend-dist` внутри runtime-образа и направляет `/api` в Symfony. Node.js и frontend dev server не участвуют в обслуживании production-запросов. Frontend и API доступны с одного origin. Домен задаётся `SERVER_NAME`; localhost-порты 8080/8443 служат стартовыми значениями и могут меняться в окружении deployment.

```text
Браузер → Caddy/FrankenPHP
          ├→ /api → Symfony → PostgreSQL / Redis cache
          └→ assets / index.html → React SPA

Messenger worker → PostgreSQL async queue / failure queue
```

Хэшированные assets получают длительный cache lifetime и `immutable`. `index.html` требует revalidation, чтобы браузер получал ссылки на assets новой сборки. API и health endpoints не получают общий публичный кэш. Сжатие статики выполняет Caddy; доступность HTTP/3 зависит также от UDP-порта, сети клиента и конфигурации развёртывания.

Proxy-заголовкам можно доверять только от известных proxy-адресов. Прямой клиент не должен задавать доверенные `Forwarded`/`X-Forwarded-*`. Когда появится CDN или внешний reverse proxy, его адреса и корректность HTTPS/host detection будут частью настройки deployment.

## Production runtime и состояние

Production использует `APP_ENV=prod`, `APP_DEBUG=0`, OPcache, realpath cache, оптимизированный Composer autoloader и прогретый Symfony cache. JIT не включается без измеренного выигрыша. Dev bundles и инструменты разработки не входят в production Composer-зависимости.

FrankenPHP worker mode сохраняет PHP-процесс между запросами. Symfony сбрасывает известное состояние в рамках жизненного цикла приложения, но будущие собственные сервисы тоже должны учитывать долгую жизнь процесса: не сохранять Request, пользователя, транзакцию или результаты конкретного запроса в mutable/static-состоянии. При необходимости реализуют механизм сброса состояния и проверяют последовательные запросы с разными контекстами. После изменения кода production workers перезапускают.

Количество PHP workers ограничивается CPU и памятью, а не выбирается по предполагаемому RPS. Стартовое `FRANKENPHP_WORKERS=2` рассчитано на небольшое окружение: Compose ограничивает web-сервис одним CPU и 768 МБ памяти, PHP web — 128 МБ на выполнение, общий максимум threads — четыре. Messenger получает отдельный PHP limit 256 МБ, мягкий лимит consumer 128 МБ и container limit 384 МБ. Это ограничение ресурсов, а не обещание пропускной способности; сумма фактической памяти процессов, threads и runtime должна укладываться в container limit.

Бюджет PostgreSQL connections учитывает все backend-реплики, Messenger workers, migrations и служебные подключения. Увеличение числа процессов без этого бюджета может перегрузить базу. Стартовые значения: `POSTGRES_MAX_CONNECTIONS=50`, `DB_CONNECTION_TIMEOUT=2` секунды, `DB_STATEMENT_TIMEOUT_MS=3000` миллисекунд, `REDIS_CONNECT_TIMEOUT=1` секунда, `REDIS_READ_TIMEOUT=1` секунда, `REDIS_MAXMEMORY=128mb`. Общий лимит PostgreSQL, timeout запросов, Redis memory и worker count уточняются нагрузочным тестом на целевом VPS.

Production-конфигурация является отправной точкой для развёртывания. Перед реальным запуском потребуются секреты вне Git, домен/TLS, резервное копирование PostgreSQL с пробным восстановлением, мониторинг, политика обновления образов и процесс применения migrations. Это эксплуатационные требования, а не уже подключённые внешние сервисы.

## Рост каталога и измерения

Размер будущего каталога 100 000–1 000 000 товаров не подтверждается пустым каркасом. Архитектура оставляет Symfony ответственным за API и PostgreSQL за источник реляционных данных, но схему, индексы и способы чтения можно выбирать только после анализа legacy и реальных сценариев.

При реализации каталога необходимо отдельно оценить ограниченную пагинацию, выборку только нужных полей, число SQL-запросов, планы `EXPLAIN`, объём ответа и пиковую память. В долгих импортах и обработчиках нельзя загружать весь каталог в ORM Unit of Work. Пакетная обработка, cursor/keyset pagination и read-модели рассматриваются по данным и требованиям; сейчас они не внедряются как скрытая бизнес-архитектура.

Минимальный smoke-сценарий проверяет только HTTP-контракт liveness с малым числом запросов. Он не измеряет каталог, checkout, работу базы под нагрузкой или качество CDN cache. Будущие эксперименты должны разделять публичную витрину с CDN cache hits, запросы к origin при cache misses, API, фоновые задачи и холодный/прогретый кэш. В отчёте фиксируют оборудование, dataset, версию сборки, concurrency/arrival rate, p50/p95/p99, ошибки, CPU/RAM, PostgreSQL connections и hit ratio.

Цель более 1000 публичных запросов в секунду на витрине с CDN относится к будущей системе. Репозиторий сейчас не доказывает достижение этой цели и не генерирует товары для её имитации.

## Точки расширения

- **Elasticsearch:** будущий поисковый индекс и отдельный адаптер чтения. Источник данных, mapping, обновление индекса, восстановление и eventual consistency определяются после анализа поиска и данных. Elasticsearch не установлен.
- **Shopify:** будущий интеграционный адаптер, секреты из окружения, проверка webhook, идемпотентность и ограничения API. Направление синхронизации и владелец данных пока не определены; SDK, credentials и интеграционный код отсутствуют.
- **CDN:** будущая доставка immutable assets и допустимого публичного контента. Правила персонализации, cache keys, invalidation и bypass определяются вместе с настоящими API. CDN не подключён.

Изменение этих точек расширения не требует переносить очередь в Redis cache или объединять frontend с PHP-шаблонами. Конкретный план миграции бизнес-логики составляется только на втором этапе; перечень необходимых исходных сведений находится в [NEXT_LEGACY_ANALYSIS.md](NEXT_LEGACY_ANALYSIS.md).
